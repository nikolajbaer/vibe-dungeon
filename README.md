# vibe-dungeon

A web-based 3D dungeon crawler in the spirit of *Ultima Underworld*, built with three.js and bitecs. The twist: it's being vibe-coded almost entirely by AI coding agents, coordinated through [GitHub Issues](../../issues), and driven from a phone rather than a workstation.

## Stack

- **TypeScript** + **Vite** — build tooling
- **three.js** — rendering
- **bitecs** — ECS for game state/logic
- **Rapier 3D** (`@dimforge/rapier3d-compat`) — real 3D collision + kinematic character control
- **GitHub Actions → GitHub Pages** — CI/CD, deploys on every merge to `main`

## How this project runs

There's no single developer at a keyboard all day — instead, short-lived coding agent sessions pick up one task at a time from [Issues](../../issues), do the work in a feature branch, open a PR, and hand it off. Because sessions are async and phone-driven, tasks need to be scoped small enough that one agent session can take a task from "todo" to a mergeable PR without needing a mid-task clarifying conversation.

**Tasks live in GitHub Issues, not here** — one issue per task, labeled by role (see below). This README stays focused on stack, status, and coordination rules.

Ground rules for keeping multiple agents from tripping over each other:

1. **One task = one PR = one owner.** Claim a task by assigning yourself its Issue before starting.
2. **PRs required, reviewed before merging to `main`.** No direct pushes to `main` — every task lands via a PR, even small ones. Feature/task branches are fine to push to directly.
3. **Small, single-purpose PRs.** Prefer several small merges over one large one — easier to review from a phone, easier for the next agent to build on a stable `main`.
4. **One agent session active at a time**, for now — pick the next open Issue off the backlog rather than starting a second one in parallel, until there's enough surface area (non-overlapping files/systems) that running a couple concurrently stops causing merge conflicts.
5. **Tasks declare their file/module footprint** where possible, so two agents don't get queued against the same files at the same time.
6. **`main` stays deployable.** CI (build + deploy) must pass before merge; don't merge on red CI.
7. **Design decisions that affect multiple systems get written down here** (in the `## Design Notes` section below) rather than living only in a chat log or a PR description, since the next agent won't have that context otherwise.

## Design Notes

### ECS conventions (`bitecs`)

Components are plain structure-of-arrays objects indexed by entity id (bitECS's recommended pattern), defined in `src/ecs/components.ts`. Systems are plain functions run in a fixed pipeline each frame (`src/game.ts`): **input → [fixed-step: npc → character → door-animation → physics → physics-sync] → door/NPC-interaction → sync-to-three.js → render**. A three.js `Object3D` is attached to an entity via the `Object3DRef` component and kept in sync by `syncSystem` — new visual/dynamic entity types should follow that same pattern rather than mutating `Object3D`s directly from other systems. Rapier handles (a `RigidBody`, a `Collider`) are attached the same way, via the `PhysicsBody`/`PhysicsCollider` side tables.

### 3D physics: Rapier + kinematic character controllers

The game originally shipped a hand-rolled collision resolver: axis-aligned XZ boxes, resolve-and-slide per axis, no `y` term anywhere. That was fine for one flat floor, but it makes verticality (stairs, multi-level tiles, anything you can stand *on top of*) impossible without reinventing a physics engine badly — so collision moved to **Rapier** (`@dimforge/rapier3d-compat`) *before* the level content that needs it, rather than after.

- **`src/physics/world.ts`** owns the whole engine surface: `initPhysics()` (awaited once at startup), `createPhysics()` (a `World` plus one shared `KinematicCharacterController`), and three builders — `addStaticBox`, `addKinematicBox`, `addCharacter`. Nothing else in the codebase imports Rapier directly, so engine-specific concepts stay in one file.
- **Characters are capsules on kinematic bodies**, moved through `computeColliderMovement` → `computedMovement` rather than by force. The controller is configured with autostep (0.4m — a real stair riser), snap-to-ground, and a 50° max climb angle, which is what will make stairs "just work" when stair tiles land. Gravity is integrated manually per character (`CharacterBody.verticalVelocity`, terminal velocity −40 m/s) since a kinematic body ignores world gravity.
- **Static level geometry has no ECS entity at all any more.** Walls, floors, ceilings and prop colliders used to each be an entity carrying `Position`/`Collider`/`Solid` purely so the resolver could query them; now `tileBuilder.ts`/`spawning.ts` create a mesh and a Rapier collider and stop. That deleted two components (`Collider`, `Solid`) and two systems (`movement.ts`, `collision.ts`) outright, and took hundreds of static entities out of `syncSystem`'s per-frame loop.
- **Collision groups** (`world.ts`) put level geometry on one layer and characters on another, with characters filtering against the level only. Characters therefore pass through each other — deliberately, since that's exactly how the old resolver behaved and changing it is a gameplay decision, not a migration one.
- **`Position` now means feet, for everyone.** It used to mean "eye at y=1.6" for the player and "feet at y=0" for an NPC. The camera's 1.6m eye offset moved into a new `RenderOffsetY` component that `syncSystem` adds on top, so `Position` is one consistent thing across every entity — which matters as soon as floors sit at different heights.
- **Fixed timestep.** Physics runs at a fixed 1/60s via an accumulator (max 5 substeps per frame, so a slow frame can't spiral), while rendering and animation stay on real frame time. Modal states (dialogue, death overlay) zero the player's velocity and reset the accumulator rather than stepping.
- **Lazy WASM.** `initPhysics()` uses a dynamic `import()`, so Vite splits Rapier's ~2.9MB of base64-inlined WASM into its own chunk instead of the entry bundle (which stayed at its pre-migration 685kB / 184kB gzipped). *Follow-up worth doing:* switching from `-compat` to the plain `@dimforge/rapier3d` package plus `vite-plugin-wasm` would ship the wasm as a real binary rather than base64, saving roughly 316kB gzipped.

### Simulated props and items

Furniture and loose world items are **dynamic rigid bodies** — they fall, stack, tip over, and get shoved by a character walking into them. This is the payoff the migration above was groundwork for, and it's authored data rather than a code path: an item is always dynamic, and a furniture asset opts in with `dynamic: { mass }` (`FurnitureAssetDef`, `assets/types.ts`). Banners and the candelabra deliberately stay static — they should read as part of the architecture.

- **A dynamic prop is the one kind of prop that needs an ECS entity.** Static geometry has none (Rapier owns the collider outright), but something has to carry the transform the simulation *produces* back to the mesh each frame — so a dynamic prop gets `Position` + `PhysicsRotation` + `Object3DRef`, written by `dynamicSyncSystem` (`ecs/systems/dynamics.ts`) and applied by `syncSystem` like any other visual.
- **`PhysicsRotation` is a quaternion, not `Rotation`'s yaw/pitch.** A chair knocked onto its side isn't expressible as a yaw.
- **Colliders are measured, not authored.** `boxShapeOf` (`level/spawning.ts`) takes a `THREE.Box3` of the finished mesh in local space and returns half-extents *plus the center's offset from the mesh origin* — necessary because this repo's meshes are built around whatever origin made the asset easiest to write (a prop's sits on the floor; the sword's sits at its grip, with most of its length out along +Z). `addDynamicBox` then keeps the body's frame on the mesh origin and offsets the collider within it, so syncing back is a straight copy with no per-asset correction. A `footprint` is only used by static props now: a body that can tip over needs a true height and center, not a floor plan.
- **Mass is the only feel knob** and is set explicitly, because Rapier's default density would make a table-sized box weigh most of a tonne. A chair (7kg) scoots from a deliberate shove and tips at ~90° if you keep pushing; the table (45kg) barely shifts; an incidental brush moves neither. Damping is well past realistic (`PROP_LINEAR_DAMPING` and friends in `physics/world.ts`) because an undamped box on a stone floor slides like it's on ice.
- **Characters push props** via `controller.setApplyImpulsesToDynamicBodies(true)` plus a `CHARACTER_MASS` impulse budget; a third collision group (`GROUP_PROP`) makes props collide with the level, with characters, and with each other.
- **Two things fell out of this for free.** The side chamber's stacked crates are now a real stack — knock the bottom one out and the top one drops — where before the upper crate was visual-only (it was explicitly skipped, to avoid burying a redundant collider inside the one below). And room-a's sword, authored at 1m over the tabletop, now *lands on the table* instead of hovering above it.
- **Consequence worth knowing:** items come to rest wherever physics puts them, usually the floor, so picking one up means looking down at it (~29° from a couple of meters out) rather than straight ahead. `pickUpItem` disables the body rather than removing it, so a future "drop" is just re-enabling it.

### Door interaction trigger (issues #6 / #7 / #26)

Opening a door fires a **raycast straight out from the camera center**; the nearest **closed** door leaf it hits within ~3m swings open on a hinge. What triggers the raycast:

- **Desktop:** press `E`.
- **Touch (issue #31, controls moved to match Minecraft mobile in a later pass):** tap anywhere on screen outside the move pad. Touch controls are a move stick (bottom-left, matching Minecraft mobile's layout — moved there from bottom-right so the layout reads as familiar) plus Minecraft-style drag-to-look — dragging a finger anywhere outside the move stick's element (and outside the attack button, bottom-right — see "Melee combat" below) turns the camera (`src/input/touchLookDrag.ts`, `TouchLookDrag`, mirroring `PointerLook`'s `consume()` pattern) instead of deflecting a second, fixed joystick. Since a tap and the start of a look-drag are indistinguishable until release, each qualifying touch tracks its total displacement from its start point: under ~10px at `touchend` counts as a tap (interact); past that threshold at any point, it's a look-drag and does not interact. Two-finger use works like Minecraft's — one finger on the move stick, the other dragging to look — because `TouchLookDrag` ignores any touch whose target lies inside the move stick's (or attack button's) element.

Doors only open (no auto-close, no "hold to open") — that's the full scope of this pass. The rest of the interaction system (issue #7 — picking up/using general items) should reuse this same "raycast from camera center, triggered by `E`/an outside-the-pads tap" convention for consistency, adding new interactable types rather than inventing a second trigger scheme.

**Interact dispatch generalized to non-door interactables (issue #36)** — `tryInteract` (`src/ecs/systems/doors.ts`) no longer assumes every interactable is a door. It builds one combined list of every `Door` and `NPC` entity's `Object3DRef`, raycasts against that whole list in a single `intersectObjects` call (which already sorts by distance, so the nearest hit across every interactable type wins), reads the hit object's `userData.eid`, and then dispatches on which component that entity actually carries — `hasComponent(world, hitEid, Door)` opens it (`openDoor`, the same pair-opening logic as before, just factored out); `hasComponent(world, hitEid, NPC)` toggles it between following/loitering (`toggleNpcFollow`, `src/ecs/systems/npc.ts`). This replaced a second, parallel raycast path that would otherwise have been added purely for the NPC. **Future interactable types (issue #7 — item pickup/use, levers, etc.) should extend this same dispatch** rather than inventing another one: give the new entity's `Object3DRef` the same `userData.eid` convention (set on whichever child mesh is actually raycastable, same as a door's slab or the NPC's mesh), add it to `tryInteract`'s combined interactable list, and add one more `hasComponent` branch that delegates to that type's own module — keeping `tryInteract` itself a thin dispatcher rather than where each interactable's actual behavior lives.

**Doors swing on a hinge (issue #26)** — each doorway is built as **two ~1.5m leaves**, hinged on opposite outer edges and swinging outward together like double doors, rather than one 3m slab. A leaf's visual is a `THREE.Group` positioned once, at build time, at the leaf's hinge point, with the door slab mesh as a child offset by half the leaf's width — `doorAnimationSystem` (`src/ecs/systems/doors.ts`) then rotates the *group* around Y from 0 to ~100° as `Door.progress` advances, which swings the slab on that hinge instead of spinning it in place. Both leaves of a doorway share a `Door.pairId`, so hitting either one with the interact raycast opens both together.

**Since the Rapier migration, the leaf's collider really swings too.** Each leaf gets a *kinematic* Rapier body at the hinge point with its cuboid collider offset by half the leaf's width (`addKinematicBox`), and `doorAnimationSystem` writes the same swing angle to both the three.js group and the body (`setNextKinematicRotation`). A door leaf therefore has no `Position` at all — hinge and body are both driven from `Door.progress` — which let `syncSystem`'s old "special-case `Door` entities out of position-sync" carve-out go away, along with the `DOOR_SOLID_UNTIL_PROGRESS` hack that used to fake "a mostly-open door isn't solid" because the box never actually moved.

### Test NPC: follow/loiter (issue #36)

A single placeholder NPC (a saturated-color `THREE.CylinderGeometry`, ~1.75m tall, spawned in `game.ts` at a hardcoded point in room-a) is the first real exercise of the collision/movement pipeline for an entity other than the player, and the first non-door consumer of the interact dispatch above:

- **Component** (`NPC` in `components.ts`): `state` (`NpcState.LOITERING` / `FOLLOWING`), a `homeX`/`homeZ` anchor, and `wanderTargetX/Z`/`wanderTimer` scratch state for its idle wander.
- **System** (`src/ecs/systems/npc.ts`, `npcSystem`, run once per fixed step right before `characterSystem`): while `FOLLOWING`, it seeks the single `PlayerControlled` entity's position, stopping once within `FOLLOW_STOP_DISTANCE` (~2m); while `LOITERING`, it gently wanders within a small radius of its home point, pausing between legs, rather than standing dead still. Either way it only ever writes `Velocity` — exactly like the player's own `inputSystem` — so the character controller moves and collides it against walls/doors the same way the player is, instead of this system moving `Position` by hand.
- **Collision generalized**: the player and every NPC carry the same `CharacterBody` component and the same kind of Rapier capsule, so `characterSystem` (`src/ecs/systems/character.ts`) resolves them all through one query with no "which one is the player" special case. Character-vs-character collision is intentionally not resolved (they can overlap) — encoded directly in the collision groups (`CHARACTER_GROUPS` filters against the level layer only), which is also exactly how the pre-Rapier resolver behaved.
- **Toggling**: interacting with the NPC (same raycast/dispatch as doors, see above) calls `toggleNpcFollow` (`npc.ts`), which flips `state` and — since "stops it, and it stays put at wherever it stopped" means the loiter anchor shouldn't snap back to the NPC's original spawn point — re-anchors `homeX`/`homeZ` (and the wander target) to wherever the NPC actually was the instant it stopped following.

### Seamless wall corners (issue #26)

`tileBuilder.ts` still emits one box per unit-cell wall segment (`WALL_DIRS`), but a segment's span is no longer always exactly `UNIT`: a second pass (`emitWalls`) first records every wall segment's two corner points, then, for each segment, extends whichever end(s) coincide with a *perpendicular* wall's corner by `WALL_THICKNESS` past the unit-cell boundary. That fills a 90° corner solidly (the two perpendicular segments now overlap in the corner square) instead of the segments only touching edge-to-edge, which is what previously read as a doubled/seamed joint. Ends that border an opening or a door are never extended, so doorway framing is unaffected.

### Tile-based level system (implemented in #21)

Levels are composed from **tiles** on a uniform grid, replacing the hand-placed geometry that used to live directly in `src/level/level.ts` (that file is now just the small orchestrator: place tiles → validate → build geometry → spawn props/items — see `src/level/tiles.ts`, `src/level/tileTypeRegistry.ts`, `src/level/occupancy.ts`, `src/level/tileBuilder.ts`, `src/level/rooms.ts`).

- **Unit = 3m.** World grid is integer cells `(x, y, z)` (y-up), each cell a 3m cube.
- **Tile type**: a footprint in cells `{w, d, h}` (width×depth×height) plus geometry and a **face map** — for every unit-cell segment on its perimeter, whether that segment is `wall`, `opening`, or `door`. E.g. a hallway is `w=1, d=3, h=1` (3m×9m footprint, 3m ceiling); a great hall is `w=3, d=3, h=2` (9m×9m footprint, 6m ceiling). Every tile type is one file under `src/level/tileTypes/` (`TileType`, `src/level/tiles.ts`), auto-discovered by `src/level/tileTypeRegistry.ts` (Vite's `import.meta.glob`, same pattern as `src/assets/itemRegistry.ts`) — a new tile type is a new file, never an edit to a shared registry.
- **Doors/openings are always centered on a single unit-cell face**, never spanning a whole multi-unit wall — so a 3-wide wall can have up to three independent connection points, one per unit segment.
- **Tile instance**: `{tileTypeId, originCell, rotation, sectorId}`, rotation in 90° steps around Y (footprint swaps w/d at 90°/270°). Instances are authored as plain data in `RoomContent.tiles` arrays, one file per room/area under `src/level/rooms/` (see "Asset-authoring system" below for the full `RoomContent` shape — the same file also carries that room's decorations/items), auto-aggregated into one list by `src/level/rooms.ts`.
- **Occupancy index**: built at load time, `cell → tileInstance`, for O(1) "what tile am I in / what's adjacent" lookups. Also used to validate at load time that every pair of adjacent instances agrees at their shared face (both open, or both wall) — a level linter, useful for the future level editor (#14) too.
- **Floors stay at a single baseline for v1** — a tile's height sets ceiling height, not floor offset. Multi-level/stairs is a separate, later feature; the Rapier migration below is the groundwork that makes it tractable (floors and steps are now real 3D colliders a character controller walks on), but no tile actually varies its floor height yet.
- **Sectors**: each tile instance declares a `sectorId` at authoring time (typically one sector = one room + its alcoves); the player's current sector is derived from the occupancy index every frame. For now this is authoring data only — no entity-activation/culling optimization is built on top of it yet. Add the actual "only simulate entities in/near the current sector" logic later, once enemy/entity counts are high enough for it to show up in profiling; with bitecs's flat typed arrays, iterating everything is cheap at the scale of a couple of rooms.
- Tile types decompose into the same wall/floor/ceiling/door boxes that `level.ts` used to hand-place, so this only replaces level *authoring* — the player/door ECS systems don't change. (Static boxes are now Rapier colliders with no ECS entity at all; see "3D physics" above.)
- See `docs/LEVEL_DESIGN.md` for the full "how to add a tile type" / "how to add a tile instance" walkthroughs, design pillars, and a worked example of the first branch off the original straight layout.

### Level viewer (menu's "View Tiles")

`src/viewer/levelViewer.ts` is an external, free-orbit look at the authored level, for checking a layout change without playing through it first-person. It calls `buildLevel` directly into its own scene/world — the exact same geometry/entities a real playthrough gets, so it can never drift out of sync with the game — then layers on three annotations that only make sense from outside: a translucent sector-colored tint per floor cell (`addSectorOverlays`, keyed by `sectorId` so two rooms authored into the same sector visually read as one), floating labeled markers for every NPC/item spawn and the player's own spawn point, and hidden ceilings (`tileBuilder.ts`'s `addSlab` tags each slab's `userData.slabKind`) so an overhead orbit camera can actually see into a room instead of just its roof. No player entity and no `npcSystem`/`characterSystem` (its Rapier world is built so the level's colliders exist, then simply never stepped) — NPCs stay put at their authored position rather than wandering, since a spawn-position marker would be pointless next to something that immediately walks away; `npcAnimationSystem` still runs so idle sway confirms "yes, this is really the same animated rig", without a `dt` from user input driving anything else.

The sector tint is genuinely necessary to actually see: from an oblique outside-the-walls angle the opaque walls occlude the interior entirely (normal depth-tested rendering — nothing special is done to see "through" them), so orbiting down close to directly overhead is how you actually confirm sector boundaries or spawn placement. A `window.__vibeDungeonViewerDebug` hook (`setCamera`, `getBounds`) exists for exactly this — automated (Playwright) verification places the camera precisely rather than approximating an overhead angle via synthetic mouse-drag deltas.

### HUD pattern: Preact + MobX (issue #23)

The HUD (health bar, and future elements like mana/inventory count/rune-spell UI) is built as a small Preact app, layered over the three.js canvas, backed by a MobX store — a separate stack from the ECS/three.js game loop, bridged deliberately rather than having HUD components read ECS state directly:

- **Rendering**: Preact components live under `src/hud/` (`.tsx` files), using the proper JSX transform via `@preact/preset-vite` (`vite.config.ts`) and `"jsx": "react-jsx"` / `"jsxImportSource": "preact"` in `tsconfig.json`. `src/hud/mount.tsx` renders the HUD root (`HUD.tsx`) once into its own overlay DOM node (`#hud-overlay`, `position: fixed; inset: 0; pointer-events: none;`), appended into the same container the touch move stick uses — new HUD elements are added as sibling components under `HUD.tsx`, each opting into pointer events on their own root element only where they actually need clicks/taps.
- **State**: `src/hud/store.ts` holds one MobX store (`hudStore`) built with `makeAutoObservable` — the function-based API, not decorators (`experimentalDecorators` fights Vite's esbuild-based TS transform). Add new HUD state as more observable fields/methods on this store (or a sibling store of the same shape) rather than inventing a second state mechanism.
- **Bridging ECS → MobX**: bitecs has no built-in reactivity, so `src/ecs/systems/hudSync.ts` is a normal system, run once per frame from `game.ts`'s pipeline (after `syncSystem`), that reads relevant player component values and writes them into `hudStore`. MobX only actually re-renders observers on a real value change, so writing unconditionally every frame is cheap. Follow this same shape for new HUD data: read ECS state in `hudSync` (or a sibling sync function), write it into the store, and let components observe the store.
- **Observing in components**: rather than pulling in `mobx-react-lite` (which assumes a React runtime and would need `preact/compat` aliasing), components use a small hand-rolled hook, `useObserved` (`src/hud/useObserved.ts`), that wraps MobX's `autorun` in a Preact `useState`/`useEffect` pair. Read store values through this hook in any new HUD component.
- **Health**: `Health` (`current`/`max`) was added to `src/ecs/components.ts` ahead of real combat (issue #16) specifically so the health bar has something to read; combat should consume this same component rather than adding its own. A debug-only key pair (`[`/`]`, handled in `game.ts`'s frame loop) nudges the player's health up/down so the reactive plumbing is visibly exercised before combat exists — harmless to leave as a permanent debug convenience.
- **Placement/phone-first**: HUD elements are positioned `fixed`, styled in `index.html`'s inline `<style>` block (matching the existing convention for the controls hint / touch joysticks), and account for `env(safe-area-inset-bottom)` since this is a phone-first game. The health bar sits bottom-center; the move-stick pad owns the bottom-left corner and the attack button (issue #48) owns the bottom-right (moved there from bottom-left in a later pass to match Minecraft mobile's move-stick placement), so keep new bottom-row elements narrow enough to fit between them.

### Inventory & equipment: items-as-entities, and UI → ECS action wiring (issue #39)

A full pickup/equip vertical slice, extending two conventions established earlier rather than inventing new ones — the generalized interact dispatch (see "Door interaction trigger" above) and the HUD's Preact+MobX pattern (see "HUD pattern" above):

- **Asset-authoring system**: every weapon/potion/curio ("item") and every piece of furniture/decor ("prop") is one self-contained file — `src/assets/items/*.ts` or `src/assets/furniture/*.ts` — that default-exports an `ItemAssetDef`/`FurnitureAssetDef` (`src/assets/types.ts`): metadata plus its own mesh factory (`createWorldMesh`/`createViewmodelMesh`/`mass` for items, `createMesh`/`footprint`/`dynamic` for furniture). `src/assets/itemRegistry.ts`/`furnitureRegistry.ts` auto-discover every file via Vite's `import.meta.glob` — adding a new asset means adding one new file, never editing a shared registry. Placement is data, not imperative calls: each room's content is one file under `src/level/rooms/*.ts` (default-exporting a `RoomContent` — `TileInstance[]`/`PropPlacement[]`/`ItemSpawn[]`, see `src/level/placementTypes.ts`) — a room's *tile instances* (which carve it out of the grid), its decorations, and its items all live together in that one file — auto-aggregated by `src/level/rooms.ts` the same glob-discovery way, and turned into real ECS entities/meshes/geometry by the generic `spawnProps`/`spawnItems` (`src/level/spawning.ts`) plus `buildGeometryFromOccupancy` (`src/level/tileBuilder.ts`). The same auto-discovery pattern covers tile *types* too — see "Tile-based level system" below. This exists because the old per-item/per-prop/per-tile-type approach collided in practice — two PRs both editing the shared body of `decorations.ts`'s `addDecorations()` function landed on the same lines and needed a manual merge. Two agents adding different assets or tile types, or decorating/extending different rooms, now touch disjoint files.
- **Item data model**: `Item` (`itemTypeId`, in `ecs/components.ts`) plus `Position`/`Object3DRef` for one lying in the world — an item *instance* is a first-class entity, mirroring how `Door`/`NPC` are entities rather than fields on the player. Picking it up (the `Item` branch of `tryInteract`, dispatched exactly like the `Door`/`NPC` branches beside it) adds `Carried` (`ownerEid`, `slot`) rather than destroying/respawning the entity; equipping/unequipping (`ecs/systems/items.ts`) only ever changes `Carried.slot` in place, between `"inventory"` and the paper-doll slots (`"head"/"torso"/"legs"/"hand-left"/"hand-right"`, only the hand ones functional today). This shape was chosen deliberately so a later container item — something else that's `Carried`-*by* rather than just carrying — fits without reworking the model, even though no container exists yet.
- **Viewmodel**: equipping a hand-slot item attaches a small placeholder mesh directly to the *camera* (`camera.add(...)`, not the scene) at a fixed camera-relative offset (`Viewmodel` in `components.ts` holds the reference) — it rides rigidly with the view like a classic FPS weapon, independent of the item's in-world pickup mesh (`Object3DRef`, just hidden via `.visible = false` while carried, not reused). Unequipping calls `mesh.removeFromParent()`.
- **Interact dispatch extended a third time**: `tryInteract` (`doors.ts`) now also collects every uncarried `Item`'s `Object3DRef` into its combined raycast list and, on a hit, dispatches to `pickUpItem` (`ecs/systems/items.ts`) — same `userData.eid` + single-`intersectObjects`-call shape as the `Door`/`NPC` branches, no second trigger path added.
- **Item pickup also works without aiming, within arm's reach**: once items became simulated rigid bodies (see "Simulated props and items" above) they mostly end up resting on the floor rather than at a convenient height, and requiring the aim-based raycast to precisely land on a small object near the player's feet felt bad. `tryInteract` falls back to `tryPickupNearbyItem` (`doors.ts`) whenever the raycast above doesn't hit (or act on) anything: it picks up the nearest uncarried item within `ITEM_PICKUP_RANGE` (1.5m/~5ft, horizontal distance only) of the player, regardless of where the camera is pointed. This is additive, not a replacement — an item farther away is still pickupable by looking straight at it, same as before.
- **Item pickup hitbox is deliberately bigger than the visual mesh**: an item's actual model can be thin (see the sword below) or otherwise fiddly to land the camera-forward interact raycast on precisely. `withPickupHitbox(mesh, eid)` (`game.ts`) wraps an item's visible mesh together with an invisible `THREE.SphereGeometry` (`ITEM_PICKUP_RADIUS`, currently 0.35m) in a `THREE.Group` — both children carry `userData.eid`, and the *group* becomes the item's `Object3DRef`. `Raycaster` tests invisible objects exactly like visible ones (`.visible` only gates rendering), so this costs nothing and needs no changes to `tryInteract` itself; it just gives every item a generous, forgiving raycast target without changing how it looks. **New item types should follow this same wrap-in-a-group pattern** rather than relying on their visual mesh's own silhouette being raycast-friendly.
- **Sword model** (issue #65): `src/assets/items/sword.ts`'s `createSwordMesh()` builds a low-poly blade/crossguard/grip/pommel from primitives merged via `mergeGeometries` (the same pattern as `humanoidRig.ts` and every `src/assets/furniture/*.ts` prop), replacing what used to be a flat `BoxGeometry` plank hand-authored separately (and slightly differently) in both `game.ts`'s world-pickup code and `items.ts`'s viewmodel code. Called once per usage site from the asset def's `createWorldMesh`/`createViewmodelMesh` (the latter scaled 0.85x for its closer camera distance) — no duplicated geometry-building. The mesh's origin sits at the grip center (not its bounding-box middle) specifically so a caller positioning/rotating it — the viewmodel's `VIEWMODEL_OFFSET` in `ecs/systems/items.ts`, in particular — pivots around the hand with the blade extending out from there, matching how you'd actually hold it. **Any future weapon/tool with a held viewmodel should follow this same shape**: a shared mesh-builder with its origin at the grip/handle, called once for the world pickup and once (scaled/tuned as needed) for the viewmodel.
- **UI → ECS action wiring (new pattern — future systems like combat will want this too)**: the HUD (`src/hud/`) only ever reads ECS state *outward* into its MobX store; nothing before this needed the reverse. The inventory UI (`src/inventory/`, a self-contained sibling of `src/hud/` with its own store/sync/components/`useObserved` rather than importing from it) needs a tap to *mutate* ECS state (equip/unequip), so `inventoryStore` (`src/inventory/store.ts`) holds an `InventoryActions` object (`{ equip(itemEid), unequip(itemEid) }`) bound once from `game.ts` (`inventoryStore.bindActions(...)`) via closures over the real `world` and `camera` — Preact components call `inventoryStore.equip`/`unequip` and never touch ECS directly, and the store defaults to no-op actions until `game.ts` binds the real ones. `equipToOpenHandSlot` (`ecs/systems/items.ts`) — not the UI — decides *which* hand slot an equip goes into, so the store's `equip(itemEid)` takes no slot argument. `src/inventory/sync.ts` (`inventorySync`, run every frame from `game.ts` alongside `hudSync`) is the one-way ECS→store direction, unchanged in shape from `hudSync`. **Any future gameplay system whose UI needs to cause a world-state change (combat's attack button, a spellcasting UI, a shop) should follow this same shape**: a plain actions interface on the store, bound once from `game.ts` with closures over whatever ECS/three.js state it needs, rather than components reaching into the world themselves.
- **Debug hooks**: `window.__vibeDungeonDebug` gained `getItemSpawns`/`getItemStates`/`getViewmodelCount` (and a `setPitch` alongside the existing `setYaw`, needed to aim the interact raycast at a specific world item during automated testing) — same pattern as the existing debug hooks, kept as permanent manual/automated smoke-testing scaffolding.

### Melee combat: its own raycast/verb, weapon-based damage, viewmodel swing (issues #48, #47)

Combat is deliberately **not** another `tryInteract` dispatch case — attacking and interacting are different verbs the player can aim at the same entity, so `tryMeleeAttack` (`src/ecs/systems/combat.ts`) runs its own short-range (2m) raycast against its own candidate list (every `Health`+`Object3DRef` entity, minus `Dead` ones and the camera's own `Object3DRef`) rather than extending `tryInteract`'s. `Dead` (`components.ts`) is a plain tag added at 0 HP; `npcSystem`'s wander/follow, `tryInteract`'s interactable list, and combat's own target list all skip it, so a corpse just sits there.

**Weapon-based damage**: `ItemAssetDef` (`src/assets/types.ts`) carries an optional `meleeDamage` — present only on actual weapons (the sword: 15), `undefined` on everything else so a future non-weapon hand item (a torch, a shield) can't accidentally zero out an attack. `tryMeleeAttack` looks up the attacker's (`PlayerControlled`) carried items in either hand slot, uses the higher-damage one if both hold a weapon, and falls back to `combat.ts`'s own `UNARMED_DAMAGE` (5) if neither hand has a weapon equipped — combat reads inventory state but inventory has no idea combat exists, same one-way dependency direction as the interact dispatch reading `Item`/`Carried`.

**Swing animation**: every attack attempt — hit or miss, since the swing is what the *player* did — calls `triggerViewmodelSwing(itemEid)` (`src/ecs/systems/items.ts`) for whichever weapon contributed the damage. `viewmodelSwingSystem(dt)`, run unconditionally every frame from `game.ts` (not just on an attack frame, so an in-progress swing keeps advancing), eases that item's `Viewmodel` mesh out from its resting `VIEWMODEL_OFFSET` pose and back via `sin(t * π)` over ~0.22s, reading `Carried.slot` fresh each frame rather than caching the hand at swing-start. **Future weapon types/animations should extend this same trigger-by-itemEid shape** rather than adding a parallel animation path — an unarmed "punch" swing, if added later, would need its own viewmodel mesh to animate the same way, since there's currently no equipped-item entity to key it off when the player is bare-handed.

### Animated humanoid characters: procedural rig + shared clips + per-instance mixer (issues #53, #54, #58, #59)

No Blender, no glTF import, no external DCC tool anywhere in this pipeline — every character asset, like every other art asset in this project, is hand-authored three.js code:

- **The rig** (`src/characters/humanoidRig.ts`, `createHumanoidRig()`) builds a bone skeleton (`THREE.Bone`/`THREE.Skeleton`, hips → spine → chest → head; hips → shoulder → upperArm → forearm → hand ×2; hips → upperLeg → lowerLeg → foot ×2 — declared as a flat `BONE_SPECS` table, each bone naming its parent by index, rather than nested literals), a single rigid-skinned `THREE.SkinnedMesh` (one box per limb segment, each vertex fully weighted to one bone — no smooth blending needed for placeholder-grade geometry), and two hand-keyframed `THREE.AnimationClip`s (`"idle"`, `"walk"`) built from `QuaternionKeyframeTrack`/`VectorKeyframeTrack`s that return exactly to the bind pose at both ends of their duration so they loop without a pop. The rig's bind pose puts the character's *feet* at local/world y=0 (not its center) — anything that spawns a character needs to set `Position.y` accordingly (see the NPC's `Position.y[npc] = 0`, changed from the old cylinder placeholder's `NPC_HEIGHT / 2`).
- **Reuse across instances**: call `createHumanoidRig()` once; each character instance gets its own mesh via `SkeletonUtils.clone(rig.mesh)` (`three/examples/jsm/utils/SkeletonUtils.js`) plus its own `THREE.AnimationMixer` — clones don't share pose state, but `rig.clips` (plain keyframe data keyed by bone name) is safe to hand to every clone's mixer directly, unmodified. Verified end to end (two clones playing different clips simultaneously, confirmed via actual bone world-position measurements, not just "it didn't throw").
- **Driving playback from gameplay state** (`src/ecs/systems/npcAnimation.ts`): `createAnimatedNpcMesh(rig, eid)` clones the rig for one entity and returns the clone as that entity's `Object3DRef` (still carrying `userData.eid`, so `tryInteract`/`tryMeleeAttack`'s existing raycasts work against it unchanged — a `SkinnedMesh` raycasts like any other `Mesh`). `npcAnimationSystem(world, dt)`, run every frame (like `viewmodelSwingSystem`), keys "walk vs. idle" off `Velocity` magnitude rather than `NpcState` directly, since `LOITERING` covers both a paused NPC and one mid-wander-leg. Per-entity mixer/action state lives in a module-local `Map<eid, ...>`, the same non-ECS-side-table precedent `combat.ts`'s `activeSwings` set — **not** a new ECS component, since nothing else needs to query "which animation is this entity playing."
- **A three.js gotcha worth knowing before touching this code**: `AnimationAction.fadeIn`/`fadeOut`'s weight ramp is a *multiplier* on the action's own `.weight`, not an absolute value, and a fully-faded-out action auto-disables itself (`.enabled = false`). Crossfading **into** an action that has already faded out once therefore requires explicitly resetting `.enabled = true; .setEffectiveWeight(1)` immediately before calling `crossFadeTo`, or the ramp multiplies against a permanent 0 and the target clip silently never becomes visible — the mixer still looks like it's running fine (clock advancing, no errors), which makes this easy to misdiagnose as something else. See the inline comment in `npcAnimationSystem`.
- **A second three.js gotcha, found while adding the death clip**: two separate `QuaternionKeyframeTrack`s that both target the same bone's `.quaternion` property (e.g. authoring a shoulder's forward-swing and its outward-splay as two independent single-axis tracks) do **not** compose — `AnimationMixer` binds one `PropertyMixer` per property path, and the second track silently clobbers the first each frame rather than combining with it (confirmed empirically: the resulting quaternion matched neither track alone nor their proper composition). A bone that needs to rotate around more than one axis in the same clip must have that combination baked into a single quaternion per keyframe up front — see `combinedRotationTrack()` in `humanoidRig.ts`, which composes multiple axis-angle rotations into one `QuaternionKeyframeTrack` rather than authoring several tracks against the same bone.
- **Hit/death one-shots** (issues #58/#59): `HumanoidRig.clips` also carries `hit` (a short, non-looping flinch) and `death` (a collapse that ends in a lying-down pose). Both are played via `THREE.LoopOnce`; `death` additionally sets `clampWhenFinished = true` so it freezes on its final frame forever rather than snapping back — that final keyframe **is** the permanent corpse pose, so it's the one that got the most deliberate authoring (see `buildDeathClip`'s comments on the hips fall + ground-height drop). `npcAnimation.ts`'s `triggerHitReaction`/`triggerDeathCollapse` pin idle/walk to weight 0 while a one-shot plays; a `mixer.addEventListener("finished", ...)` handler hands control back to idle/walk once `hit` (only) finishes, resuming whichever of the two `moving` has become in the meantime rather than crossfading back in (the interrupt already popped visually, so there's nothing to blend from).
- **Corpses persist until the player leaves their death sector**: `combat.ts`'s kill branch no longer removes the mesh outright — it triggers the death collapse instead, and `game.ts` records which sector (`level.sectorAt`) the entity died in, via a new `DeathSector` component. `corpseCleanupSystem` (`ecs/systems/corpseCleanup.ts`), run every frame with the player's current sector, removes a corpse's mesh (once) the first time that sector no longer matches — a one-way cleanup, not a presence toggle; the corpse never reappears. This is the first real gameplay consumer of the sector-tracking data that's existed since the tile system (previously "authoring/tracking data only").
- **Future animated characters/clips should extend this same shape**: a `HumanoidRig`-shaped factory function, `SkeletonUtils.clone` per instance, a small `Map<eid, ...>`-keyed system for anything state-driven, `combinedRotationTrack` for any bone that needs more than one rotation axis per clip.

### Moody torch-driven lighting (issue #64)

The dungeon used to be lit almost like daytime — a flat white `AmbientLight(0.55)` plus an outdoor-style `DirectionalLight(0.85)` positioned like a sun, which washed out the warm torch `PointLight`s (`src/level/tileBuilder.ts`, `addTorch`, issue #41) that were supposed to be the dungeon's actual light source. `startGame` (`game.ts`) now sets a dim, cool blue-grey `AmbientLight` plus a very dim `HemisphereLight` (sky/ground fill, standing in for bounce light rather than a directional sun that doesn't belong indoors), `renderer.toneMapping = THREE.ACESFilmicToneMapping` (so torch highlights roll off instead of clipping to flat white), and `renderer.shadowMap.enabled = true` with each torch `PointLight` casting a small shadow map — walls/floor/ceiling `receiveShadow`, walls also `castShadow`. Torches now read as the dominant, directional light source: real pools of warm light around each one, genuine shadowed corners, darkness in between.

**The ambient/hemisphere floor needs to stay non-zero, not just "dim"** — the first landed values here measured as literal `(0,0,0)`-`(3,1,1)` 8-bit pixels (not just "very dark," but fully clipped to black) on a wall a couple meters from any torch, once run through ACES's shadow rolloff; confirmed by sampling raw pixels from an actual rendered screenshot, not by eyeballing a thumbnail. A player standing in front of a door or wall they need to interact with seeing pure undifferentiated black fails "moody" into "broken" — if retuning these values, verify a spot with no nearby torch renders as *dim but shaped* (walls/doors distinguishable as darker or lighter shapes against each other), not blank.

**Perf**: torch shadow maps are kept small (256×256) and use three's cheaper default `PCFShadowMap`; this project has no performance-profiling infrastructure, so if shadows ever need to be cut for frame-rate reasons, `renderer.shadowMap.enabled = false` in `game.ts` is a clean, independent rollback — nothing else in the lighting setup depends on shadows being on.

### Procedural stone textures (issue #11)

`src/materials/textures.ts` and `src/materials/dungeonMaterials.ts` are a standalone pair of modules — not imported by anything yet — providing placeholder-grade stone looks with no image assets and no noise library:

- `textures.ts` implements small hashed-noise primitives (a bit-mixing `hash2`, toroidal value noise/fbm, and toroidal Worley/cellular noise) and `createStoneTexture(opts)`, which draws one of three seamlessly-tileable patterns (`"coursed"` block masonry, `"flagstone"` crazy-paving, or `"flat"` low-contrast) onto a `<canvas>` and returns a `THREE.CanvasTexture` with `RepeatWrapping` already set. All the noise sampling wraps toroidally so there's no seam at the tile edges.
- `dungeonMaterials.ts` exports `wallMaterial(repeat?)`, `floorMaterial(repeat?)`, and `ceilingMaterial(repeat?)`, each returning a ready-to-use `THREE.MeshStandardMaterial` (rough, non-metal) built from a cached base texture. Each source texture is authored to represent one 3m project grid unit with individual stone blocks ~0.3-0.6m; `repeat` (default 1, a number or `[x, y]`) is an extra multiplier for surfaces bigger than one grid unit.

**Intended follow-up hookup** (not done here, to stay out of the parallel tile-system work): now that the tile-based level system's `src/level/materials.ts` exists with its own `wallMaterial()`/`floorMaterial()`/`ceilingMaterial()` functions (currently flat-colored `MeshStandardMaterial`s), swap their bodies to construct and return `dungeonMaterials.wallMaterial(...)` etc. instead, passing a `repeat` scaled to each tile/face's real size in meters (e.g. `faceSizeMeters / 3`) so stone blocks keep a consistent real-world scale rather than stretching. This should be a small, self-contained change confined to that one file.
